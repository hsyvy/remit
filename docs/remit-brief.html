Remit

Your agent spends within its remit.

A spending wallet for AI agents. To remit is to send money, and a remit is the limit of what someone is allowed to do. Remit is both. The agent asks you for a budget ahead of time, explains what it needs the money for, and can only spend what you approved on PayPal. Whatever it doesn't spend goes back to you.

The problem

Agents can shop now. Nobody wants to hand them a credit card.

Shopping agents can already find products, compare prices and fill out checkouts. The missing piece is trust. Today you either approve every single purchase, which defeats the point of an agent, or you give it a saved card and hope it behaves. A page with hidden instructions, a misread request or a pricing bug can turn into real charges.

Fixed rules like "max $50 per item" help, but they are static. A grocery week, a holiday week and a quiet week need different budgets, and the user has to keep editing settings.

Remit changes the question. You stop approving each purchase. You approve a budget the agent proposes, with reasons, for a set period. Inside that budget the agent acts on its own. Outside it, the agent has to ask you again.

Guarantees

Four rules the product never breaks

Only you approve money

Every budget and every top-up is approved by you on PayPal's own page, signed in to your PayPal account. The agent has no way to approve its own request.

It can't overspend

Each purchase is checked against the remaining balance in server code before it's paid, and PayPal itself refuses to capture more than the hold. A prompt can't change either check.

Unspent money comes back

The budget is a hold on your PayPal funds, not a transfer. Only what the agent actually spends is taken. The rest is released when the period ends.

Every dollar has a reason

Each purchase links to a line in the approved plan, with the product, price and the agent's reasoning. You can ask the wallet why it spent anything.

The core idea

A budget request, written by the agent

This is where the AI earns its place. Before each period, Claude reads what it knows about you, then drafts a spending plan and explains each line:

  • Spending history from earlier weeks in the wallet's ledger (and PayPal transactions, if you connect them).
  • Things that are running out, based on how often you reorder them.
  • Tasks you gave it, like "find a birthday gift for Sam by Friday".
  • Current prices, looked up through Channel3's product search, so the estimates aren't guesses.

You can approve the plan as is, remove lines or change amounts, or decline it. If something comes up mid-week, the agent sends a smaller top-up request with its reason, which you approve the same way.

How the money moves

One period, start to finish

The budget is a PayPal authorization: a hold on the user's funds that the platform can capture in pieces. Each purchase is a partial capture. PayPal holds funds for up to 29 days, which is enough for a one-week wallet.

Architecture

Five parts

  1. Wallet service (Node/TypeScript). Owns the ledger (SQLite), the PayPal credentials and every money rule. The only part that talks to PayPal for money.
  2. Agent (Claude with tool use). Its only money tools are get_balance, request_budget, request_topup and spend, served by the wallet. It never sees PayPal keys.
  3. Product search (Channel3 API). Real products, prices and buy links for planning and shopping.
  4. Web app. A chat with the agent, the wallet meter, budget requests to approve, and the ledger with reasons.
  5. Wallet MCP server. The same four tools exposed over MCP, so other agents (Claude Desktop, Cursor, any MCP client) can use the wallet too.

Rule of thumb for the build: if a check protects money, it lives in the wallet service, never in the prompt.

Design decisions

Hold or prepaid

There are two ways to give the agent money on PayPal. I recommend the hold, and keeping prepaid as the fallback if the sandbox test on day 1 shows a problem.

Risks to check on day 1

Three things the sandbox has to confirm

1. Captures after the 3-day honor period

PayPal guarantees funds for 3 days. Between day 4 and day 29 a capture usually works but "is subject to risk and money availability". Plan: the wallet re-authorizes the remaining amount after day 3 (allowed within the original approval, so you don't need to approve again). If a capture still fails, the agent asks you for a new budget.

2. Releasing the leftover after partial captures

PayPal refuses to void an authorization that has already been captured (PREVIOUSLY_CAPTURED). So the period has to end with a capture marked final_capture: true. Test whether that releases the rest of the hold right away. If it doesn't, the fallback is the prepaid model, where the leftover is an explicit refund.

3. Who gets paid in the sandbox

Captures land in Remit's sandbox business account. The sandbox can't buy from real stores, so the demo finds real products through Channel3, takes the payment from the hold, and simulates the store's checkout. The write-up says so openly. The production path is the platform paying the store (PayPal Payouts) or stores accepting agent payments directly.

Room to innovate

Where it can go further

Blue items are in scope for this week. Amber items are stretch goals if the core is done by Nov 9. Grey items go in the pitch as the roadmap.

This weekAgentic Commerce

Wallet as an MCP server

Any agent gets a budget, not only ours. Connect Claude Desktop to the wallet and it can shop safely under your approved limit. This is the "infrastructure" angle that sets it apart from one more shopping bot.

This weekPayPal + AI

Plan lines as envelopes

Each approved line becomes its own small budget. The agent can't spend gift money on groceries without asking. Gives you control without per-purchase approvals.

This weekSecurity

A second opinion before each purchase

A separate Claude call, with no access to the web page the agent was reading, checks that the purchase matches the approved line. Code catches the amount. The reviewer catches intent, like a product page that tricked the agent.

StretchDesign

Forecasts that learn

At the end of each period, compare the plan with what was actually spent and show how accurate the agent was. Better track record, tighter buffers, smaller holds.

StretchOpen source

Hold tools for the PayPal Agent Toolkit

Contribute authorize_order, capture_authorization and void_authorization upstream. The judges include PayPal developer advocates who maintain these tools.

StretchRender

Scheduled close-out

A Render Workflow closes each period, releases the leftover, drafts next week's plan and sends you the approval link. Also qualifies for the Render prize.

RoadmapMost Impactful

Family and team wallets

Several agents, each with its own wallet, all approved by one parent or manager. A teen's allowance agent, a team's software-purchase agent.

RoadmapMost Creative

Agents paying agents

A research agent buys a dataset from another agent's service. Both sides run on wallets, so neither can be drained.

RoadmapAG Grid

Ledger in AG Studio

Turn the ledger into an AG Studio dashboard and let the agent build widgets on request ("show gift spend by month"). Only worth it if aiming for the AG Grid prize.

Hackathon fit

Prizes and judging

Prizes it targets. Best Use of Agentic Commerce, Best Use of PayPal + AI, plus the Channel3 sponsor prize. Render if we host there. One project can win one top-three or $5K award plus one sponsor prize.

Judging criteria, which carry equal weight:

  • Technical: real holds, partial captures, refunds, webhooks and an agent with tool use. It goes well beyond a single checkout button.
  • Design: one coherent flow, from request to approval to spending to close-out, with a meter you understand at a glance.
  • Impact: it solves the trust problem that keeps people from letting agents spend.
  • Originality: the agent writes and justifies its own budget, and the wallet works with other agents over MCP.
  • Presentation: the refused purchase and the top-up request make a clear moment in the video.
