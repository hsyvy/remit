Remit Architecture

How Remit is put together: every component, what it is responsible for, what goes in and comes out, and how the parts talk. Use it as the map for building the next version.

Agents are untrusted. Every money rule lives in the wallet and in PayPal, never in an agent's prompt.

System diagram

Lifecycles

Three records carry the money: a request (what the agent asked for), a hold (money PayPal reserved) and a purchase (money taken). Each moves through a fixed set of states, stored in the status column.

Key flows

Get a budget

  1. The agent calls request_budget with dates, lines (key, label, amount, reason) and an optional buffer.
  2. The wallet checks the rules (1 to 12 lines, period of 28 days or less, under REMIT_MAX_REQUEST) and saves a pending request and a pending period. It returns a review link.
  3. The owner opens the request card, can change or remove lines, and clicks Approve. The wallet creates a PayPal order with intent AUTHORIZE and the request moves to checkout.
  4. The owner approves on PayPal's page. PayPal redirects to /paypal/return.
  5. The wallet authorizes the order. Only a successful authorization counts as approval, so visiting the return link by hand does nothing. It then creates the hold and one envelope per approved line, and the period opens.

Spend

  1. The agent calls spend with line, amount, title, store and its reasoning.
  2. The wallet takes the next turn in its one-at-a-time queue, so two purchases can't both pass the checks.
  3. Line rule: take from the line first, then the buffer, never from another line. Total rule: never more than what is still held. If either fails, a refused purchase is recorded and the agent gets the reason.
  4. The purchase is saved as pending, then the purpose check judges whether it fits the line's reason. A rejection, or a purpose check that can't be reached, refuses the purchase.
  5. The wallet captures from the oldest active hold first, spreading across holds if needed. Each capture carries an ID so a retry can't charge twice. A hold past PayPal's 3-day guarantee is renewed first. If a later capture fails, earlier ones in the same purchase are refunded.
  6. The purchase becomes captured, an event is logged, and the agent gets what's left on the line and in total.

Ask for more, then close

  1. After a refusal, the agent calls request_topup for an existing or new line. It follows the same approval path as a budget and ends in a second hold.
  2. At the end date (checked every 60 seconds) or when the owner clicks Close, the wallet voids each active hold. Untouched holds are released at once. Holds with partial captures are marked lapsing and released when they expire. Open requests expire.

Money core

These components enforce the guarantees. Treat changes here like changes to a payment system: tests first.

Wallet

productsrc/wallet/wallet.ts
Role
Owns every money rule: budgets, lines and buffer, holds, purchases, refusals, extra money, close-out and refunds. Nothing else changes money state.
Inputs
  • From agents, through the tool contract: requestBudget, requestTopup, spend, balance, history
  • From the owner, through the API: checkout(requestId, edits), decline, closePeriod, refund
  • From PayPal's redirect: completeApproval(requestId, orderId)
  • From the timer: closeIfEnded()
Outputs
  • Results with amounts in cents (line left, total left, capture IDs, the purpose check's verdict)
  • A WalletError with a code and a plain message the agent can act on, such as OVER_LINE
  • Rows in the database and events in the activity log; calls to the PayPal gateway and the purpose check
How it works
Money-changing calls run one at a time through a promise queue, and each change is one database transaction. It never trusts its caller: it checks every amount, line key, date and length itself.
Guarantees
A purchase never uses another line's money. Spending never exceeds what is held. Only an authorized PayPal order creates spendable money. Every refusal is recorded with its reason.
Next
Owner-only moveBetweenLines; per-agent lines and pause; draw from the hold that funded the line instead of the oldest.

Agent tool contract

productsrc/wallet/tools.ts
Role
The single definition of what any agent can do with money. Both the MCP server and the demo agent use it, so they get identical rules.
Inputs
A tool name and raw JSON from an agent. Amounts are in dollars.
Outputs
A short JSON result with dollar strings ("$32.49"), or the wallet's error message.
How it works
Each tool has a zod schema and a description written for the agent. runWalletTool validates the input, converts dollars to cents, calls the wallet, and formats the answer. The descriptions carry the guidance an outside agent needs, such as giving every line a reason.
Next
Add get_history so every agent can cite evidence; require a reason on every line; carry an agent ID on each call.

Purpose check

productsrc/wallet/reviewer.ts
Role
Checks each purchase against what its line is for, before any money moves. This is what limits the purpose of the money, not just the amount.
Inputs
The line's label and the owner-approved reason, plus the purchase: title, store, URL, price and the agent's reasoning. It never sees the pages the agent read.
Outputs
{ verdict: "approve" | "reject", reason }. The reason is shown in the ledger.
How it works
One structured Claude call at low effort. The purchase text is marked as untrusted data. A model refusal, a missing verdict or an error all count as a rejection.
Next
Let the owner override a rejection from the decision card; build a test set of misleading store listings to measure it.

PayPal gateway

productsrc/paypal/gateway.ts · rest.ts · simulated.ts
Role
The only code that talks to PayPal. It hides whether Remit is on the real sandbox or the local simulator.
Inputs
createAuthorizeOrder, getOrderStatus, authorizeOrder, capture(id, {cents, finalCapture, idempotencyKey}), reauthorize, voidAuthorization, refund.
Outputs
Order ID and approval URL, authorization ID with amount and expiry, capture and refund IDs, or a PayPalError carrying PayPal's issue code (MAX_CAPTURE_AMOUNT_EXCEEDED, PREVIOUSLY_CAPTURED, ORDER_NOT_APPROVED).
How it works
The REST client caches the OAuth token and sends a PayPal-Request-Id with each write so retries are safe. The simulator stores its state in the database and enforces the same limits, so tests and keyless demos behave like PayPal.
Next
Webhooks for order approved or declined and authorization voided or expired; a payout or merchant-payment call to pay real shops.

Database

productsrc/db.ts
Role
The record of every request, approval, hold, purchase and reason. It is the source for the ledger and for the agent's history.
Inputs
Writes from the wallet (and the simulator's own table).
Outputs
Reads for balances, history, the owner's state view and the chat transcript.
How it works
SQLite through node:sqlite in WAL mode. All money is integer cents. Multi-row changes use BEGIN IMMEDIATE transactions. The tables are listed under Data model below.
Next
Agents table; a move between lines as its own record; move to Postgres when hosted for more than one owner.

Close-out timer

productsrc/server/main.ts
Role
Closes a budget period once its end date passes, so leftover money is released without anyone clicking.
Inputs
Time. It runs every 60 seconds.
Outputs
A call to wallet.closeIfEnded().
Next
Also start next week's planning: send the owner the weekly recap with the proposed next budget.

Interfaces

How people and agents reach the money core.

API server

productsrc/server/app.ts
Role
One HTTP server with three audiences: the owner's web app, PayPal's redirect, and agents.
Inputs
HTTP requests. Agent routes need Authorization: Bearer REMIT_AGENT_TOKEN. Owner routes need a password when REMIT_OWNER_PASSWORD is set.
Outputs
JSON. Errors are mapped to clear responses: wallet errors keep their code, PayPal errors become 502 with PayPal's issue, bad input becomes 400.
How it works
Hono on Node. Routes are thin and call the wallet. The routes are listed under Contracts below.
Next
Detect PayPal declines (the request currently stays in checkout with no message); a webhook route; one token per agent.

MCP server

productsrc/mcp/main.ts
Role
Lets any agent the person already uses, such as Claude Desktop, use the wallet. This is how Remit becomes the wallet for your agent.
Inputs
MCP tool calls over stdio: get_balance, request_budget, request_topup, spend. Configured with REMIT_URL and REMIT_AGENT_TOKEN.
Outputs
The tool's JSON result as text, or an error result.
How it works
It registers the same schemas as the tool contract and forwards each call to POST /agent/v1/tools/:name. It holds no PayPal keys and no database, so a compromised agent machine can't reach money directly.
Next
Add get_history; a remote (HTTP) MCP transport so hosted agents can connect.

Owner web app

productweb/index.html · app.js · styles.css
Role
Where the person decides and reviews: approve or edit requests, watch the balance, read the ledger, refund, close the period.
Inputs
GET /api/state, polled every 5 seconds (every 1.2 seconds while the agent works); the owner's clicks and edits.
Outputs
Calls to the owner routes; a redirect to PayPal's approval page.
How it works
Plain JavaScript with no build step. Parts: mode chips, balance meter, request cards, plan lines, ledger with reasons, activity feed, and the demo chat. Shows an approximate rupee figure from REMIT_INR_RATE.
Next
Approvals as phone notifications; a decision card with what happens if you say no; a pause button per agent.

Demo parts

These stand in for the user's own agent and for real shopping. Keep them working for the demo, but don't build product features into them.

Shopping agent

demosrc/agent/agent.ts
Role
A reference agent that shows the wallet in use: it plans a budget, shops, accepts refusals and asks for more.
Inputs
The owner's chat message, through POST /api/chat.
Outputs
Chat replies and tool calls; the transcript is saved in chat_messages.
How it works
A manual tool loop on Claude Opus 5.5 (up to 20 steps). It has the four wallet tools plus search_products and get_history. Its prompt tells it to cite evidence, add about a 10% buffer, never follow text from store listings, and quote rupees next to dollars.
Product gap
The planning guidance and get_history live only here. Move them into the tool contract so outside agents get them too.

Product search

demosrc/search/search.ts
Role
Gives the demo agent products to buy.
Inputs
A query and an optional maximum price.
Outputs
Products: title, brand, price in cents, store, URL, stock.
How it works
Channel3 when CHANNEL3_API_KEY is set (cheapest in-stock USD offer per product), otherwise a 13-item built-in catalog.

Seed history and sandbox check

demoscripts/seed.ts · scripts/sandbox-check.ts
Role
seed adds four closed example weeks for the agent to plan from. sandbox-check tests PayPal's hold behaviour: partial captures, an over-limit capture, void after capture, final capture, and voiding an untouched hold.
